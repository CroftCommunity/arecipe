## 0. The question

When an event a subscriber has already fetched **disappears from a subscribed
`.ics` feed**, does the subscriber remove it from the user's calendar, or does it
persist indefinitely? Primary target: **Google Calendar**. Secondary, if cheap:
Apple Calendar, Outlook.

Two behaviors, opposite consequences for the 90-day window RUN-LAST-PLANNED
ships:

- **Drop** — the user's calendar quietly loses last spring's dinners as they age
  out of the served file. The window does real work on the user's calendar, and
  the setup page must say so.
- **Retain** — the calendar accumulates forever; the window only bounds the file
  we serve, not what the user sees. Different copy, arguably a different default.

No authoritative source settles this: Google does not document subscribed-feed
replacement semantics, and forum/blog material is inconsistent. **Both outcomes
are live** until this experiment resolves them.

---

## 1. Why this blocks the window shipping

The calendar-setup page needs one true sentence about what happens to old meals.
That sentence is different under *drop* vs *retain*, and if *omission* drops but
*cancellation* retains (or vice-versa) the **assembler design** changes too: a
bounded tail of `STATUS:CANCELLED` tombstones instead of a silent truncation.
So the window's *value*, the *copy*, and possibly the *assembler* all wait on
this result.

---

## 2. Method

Two arms, each a separate feed URL and a separate subscription, so they cannot
contaminate each other.

**Arm 1 — silent omission.** Subscribe to Feed A (E1, E2, E3). Once all three
appear, replace it with Feed B: **E1 removed entirely**, E2 and E3
**byte-identical**. Poll daily up to 7 days; record if/when E1 disappears.

**Arm 2 — explicit cancellation.** Subscribe to a *second* Feed A on a *different*
URL. Replace with a Feed B that **keeps E1 as a `STATUS:CANCELLED` /
`SEQUENCE:1` tombstone** instead of removing it; E2, E3 byte-identical. Poll
identically. Cancellation is the standards-blessed retraction and may behave
differently from omission — if it works where omission does not, the assembler
can emit tombstones for a bounded tail.

The three canonical events (dates fixed from base **2026-07-23**):

| Event | Offset | Date (`DTSTART`) | UID |
|---|---|---|---|
| **E1** | −60 days | `2026-05-24` | `exp-ics-window-e1@arecipe.app` |
| **E2** | −30 days | `2026-06-23` | `exp-ics-window-e2@arecipe.app` |
| **E3** | +7 days  | `2026-07-30` | `exp-ics-window-e3@arecipe.app` |

All are all-day (`VALUE=DATE`, exclusive `DTEND`), matching the product's real
meal-plan feeds, so the observation is representative of what arecipe ships.

## 5. The feed builder (real code, tested — §5 of the plan)

Per the experiment's TDD note, the feed generator is real code and was tested
**before** it produced a single probe file. It is a **pure function** from an
event list to `.ics` text, clock-free (DTSTAMP injected), living under `tools/`
(lint/typecheck-ignored ops scratch — **no product code ships**).

- `tools/ics-window-probe/feed.mjs` — `buildProbeIcs(events, opts)`, `cancel(ev)`,
  `toIcalStamp(iso)`.
- `tools/ics-window-probe/feed.spec.mjs` — **14 tests, all green** (RED-first: the
  spec was written and run failing before `feed.mjs` existed).

Coverage demanded by the plan, all present and passing:

- **UID stability** — the UID is emitted verbatim, and a retained event (E2, E3)
  is asserted **byte-identical** between Feed A and Feed B in both arms. This is
  the invariant that makes the experiment valid: the only change a subscriber can
  react to is E1.
- **`SEQUENCE` increment** — base events emit `SEQUENCE:0`; `cancel()` bumps to
  `SEQUENCE:1` (and preserves UID + date).
- **`STATUS:CANCELLED` emission** — absent on a normal event; present, with the
  VEVENT retained, on a cancelled one.

## 7. Recommendation — decision tree (fill the branch the run selects)

The recommendation is **conditional on the arm-1/arm-2 outcomes**, given here in
full so the runner reads the answer off the observed result rather than
re-deriving it. **Do not pre-select a branch** — §0 holds both outcomes live.

### (a) Window value

- The 90-day value stands regardless; it bounds the **served file** (parse cost,
  bytes, and — under *drop* — the user's calendar tail). Nothing observed here
  argues to change the number itself. Confirm after the run that 90 days is
  comfortably outside whatever refresh/propagation latency arm 1 shows.

### (b) Emit cancellation tombstones?

| Arm 1 (omission) | Arm 2 (cancellation) | Assembler recommendation |
|---|---|---|
| DROP | (any) | **No tombstones needed.** Silent truncation at the window already removes aged meals from the user's calendar. Simplest assembler. |
| RETAIN | DROP | **Emit tombstones for a bounded tail.** Omission strands old meals; explicit `STATUS:CANCELLED`/`SEQUENCE:1` is what actually removes them. Emit tombstones for events leaving the window for a bounded number of days, then let them fall off. |
| RETAIN | RETAIN | **Tombstones don't help; do not bother.** Neither mechanism removes the event. The window bounds only the file; the user's calendar accumulates. Say so in copy (branch c, RETAIN). |
| AMBIGUOUS | AMBIGUOUS | **Record ambiguous. Ship the conservative copy** (branch c, RETAIN) and do not promise removal. Re-run later if it matters. |

### (c) The exact calendar-setup sentence

Pick the line matching the resolved behavior; keep it descriptive of what we
observed and when, never a promise about behavior we don't control (§8).

- **If DROP (omission removes):**
  > "Meals older than about 90 days drop off your subscribed calendar
  > automatically — when a meal ages out of the feed, Google Calendar removed it
  > in our testing (observed July 2026)."

- **If RETAIN + tombstones adopted:**
  > "Your subscribed calendar keeps roughly the last 90 days of meals. Older
  > meals are retired from the feed; some calendar apps clear them and some keep
  > a copy — you can delete any you no longer want."

- **If RETAIN, no removal mechanism works:**
  > "Meals you've already added to a subscribed calendar stay there even after
  > they age out of arecipe — subscribing keeps a growing history. Remove old
  > meals in your calendar app if you'd like a tidier view."

- **If AMBIGUOUS:** use the RETAIN-no-removal wording above — it is true under the
  widest set of behaviors and promises nothing we can't back.
